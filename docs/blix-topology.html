01 — the line

Engine and consumer, and the four things that are genuinely arguable

The split is cleaner than it feels from inside. The engine is a library stack that never names a game; every consumer is an executable, or a lab library serving one. What is worth arguing about is a short list, and each entry on it is a restructuring decision waiting to be made.

Blix/SkinnedGameObject.cs
121 ln · in the engine · 1 consumer

A skinned model you can draw, offered to everyone. VulkanLit took it. Runner, Bulwark, RTSGame and the toolchain lab each wrote their own instead — because it bakes in a draw, and the draw is the part that differs.

Blix.Render/PropModel.cs
686 ln · in the engine · 1 consumer

The same story one layer up, and the largest file in Blix.Render. Only RTSGame uses it. Two engine-side attempts at one abstraction, both stranded, both for the same reason.

Blix.Labs.Toolchain/LabRig.cs
458 ln · outside · 2nd consumer arriving

glTF import, GPU buffers, textures, bounds, weighted-bone analysis — then a bone material that names a shader. The first half is what the character lab would otherwise copy. The second half is what stranded the other two.

Blix.Labs.Character/BodyResolver.cs
183 ln · outside · stays out

Sweep-and-slide. Its math already moved into Blix.Geometry; the loop did not. The camera was expected to be its second consumer and turned out to want one cast and a clamp — decided by evidence, not deferral.

The pattern in all four: geometry and loading travel; a draw does not. An abstraction that names a shader program, a material set or a pass has an owner whether it admits one or not.

04 — the register

Every consumer, and what it is for

Twenty-four projects in four families. Descriptions come from each project's own header block — most demos carry an explicit proves / intentionally owns pair, which is the convention that keeps a demo from quietly becoming a game.

Demos

11 executables · 10,430 ln

Roughly two kinds, and the tree does not label which is which. The first five are executable specs — deliberately minimal call sites that exist so a primitive has a known-good consumer. The last four are games that grew from one.

Blix.Demos.Chassis
exe149 ln4 deps

The smallest application that can exist, and an executable spec for the chassis itself. It answers two questions nothing else can, because every other app is also a diagnostics producer: does an app get a UI without being IDebuggable, and does UI capture actually suppress game input. Deliberately not IDebuggable.

tools/run-chassis.sh
Blix.Demos.VulkanHello
exe511 ln8 deps

A spinning lit cube — the narrowest known-good Vulkan path: depth attachment, descriptor sets, per-frame UBO, name-keyed ShaderUniform through a UniformBlockLayout. Kept minimal on purpose so it is the simplest reference call site when something further up the stack breaks.

tools/run-vulkan-hello.sh
Blix.Demos.VulkanInstanced
exe180 ln7 deps

The instancing proof gate: 5,000 cubes in one vkCmdDrawIndexed, each reading its transform and tint from a set-3 SSBO. Auto-exits after more frames than there are frames in flight, so both replicated SSBO slots are written and bound at least once — which is what would surface an in-flight hazard.

tools/run-instanced.sh · assert under BLIX_VK_VALIDATE=1
Blix.Demos.VulkanGraph
exe372 ln8 deps

Render-graph validation in three passes: a cube into an HDR offscreen, an invert pass reading it through a graph Read edge, then an imperative present. If the edge is wired the cube appears inverted; if it is broken the present shows garbage. The failure is visible rather than silent, which is the whole design.

Blix.Demos.VulkanParticles
exe647 ln8 deps

Three CPU-simulated effects — a spark fountain with drifting smoke, a periodic explosion, a swirling vortex — riding the per-frame transient vertex arena through an HDR bloom pipeline with soft-particle depth fade. ParticleBatch stays pure geometry: the demo brings the pipeline, the push and the depth binding.

tools/run-particles.sh
Blix.Demos.VulkanLit
exe1,856 ln8 deps

PBR end to end: cube, skinned glTF, PBR spheres and ground under a sun, two spots and a point light, each with PCF shadows, plus procedural-sky IBL, HDR bloom and ACES tonemap. Shadow passes → lit scene → bloom → present.

It is also the only consumer of Blix/SkinnedGameObject.

Blix.Demos.VulkanSponza
exe2,329 ln11 deps

The Khronos Intel Sponza scene — the renderer's performance and asset-pipeline proving ground, and the most dependency-heavy project in the tree. Cooked siblings only (.blixtex, .blixprobe, .blixmesh with LOD chains). Shadow cascades → optional froxel fog → depth pre-pass → 4× MSAA lit scene → tonemap.

The tree's only consumer of Matrix4x4ArrayUniform, and therefore the only thing that would exercise the record-time array freeze. Its asset pack lives on an external SSD, so it is currently unverified.
tools/run-vulkan-sponza.sh · needs BLIX_SPONZA_ASSETS
Blix.Demos.Pong
exe711 ln10 deps

The 2D game proving the Vulkan SpriteBatch + Font path with a CRT post-FX finish. Gameplay runs in a virtual playfield; sprites render to a 2× offscreen through a Vulkan-NDC ortho, then a CRT shader downsamples to the swapchain. Owns its rules, physics, scoring and look.

Known fault, attributed and unfixed: destroys pipeline, buffer, framebuffer and render pass while a command buffer still references them.
tools/run-pong.sh
Blix.Demos.Runner
exe849 ln10 deps

A 3D endless runner — the instancing plus skeletal-animation showcase. The world flows toward the camera and wraps procedurally; ground, barrels and coins each draw through a per-mesh InstancedBatch, and the player is a skinned glTF character on the bone-palette path whose run cadence tracks speed and switches to a jump clip mid-air.

Its CC0 KayKit Rogue is the tree's reference rig — 41 bones, 76 clips — and the subject of every toolchain and character lab capture.

tools/run-runner.sh
Blix.Demos.TankArena
exe1,335 ln9 deps

A survival shooter built on Transform3D parenting. Each tank is a hull → turret → barrel hierarchy: driving the hull carries the turret, which yaws independently. Shells spawn as a child of the firing barrel, then SetParent(null, keepWorldPose) detaches them into a physics arc — the parenting model's detach op, demonstrated rather than described.

Its enemy steering was the first consumer to pressure a navigation primitive.

tools/run-tank.sh
Blix.Demos.Bulwark
exe1,491 ln9 deps

Tower defence, game #2, built specifically to pressure axes Runner, Pong and TankArena left alone: pointer-driven picking, navigation, and a skinned animated crowd through skinned-mesh instancing. Sun shadow → HDR scene → present, with a SpriteBatch HUD on the present pass.

Its nav and turret rig were deliberately not extracted.

Labs

2 libraries + 6 executables · 9,459 ln

The pattern both families share: one library holds the scene, shaders and renderer; several thin executables ask different questions of it. A viewer you drive, a probe that judges and exits non-zero, a capture that writes a PNG. None of the executables declare shaders or render code.

Blix.Labs.Toolchain
lib2,321 ln3 consumers

The toolchain lab's library — LabRenderer (676), LabRig (458), RigSession (363), LabSkeletonView (267), LabModel (247), plus camera, scene and geometry. Subject: assets and the binding model — what a glTF file actually contains and how it reaches the GPU.

Blix.Labs.Toolchain.Viewer
exe1,711 ln7 deps

Chassis conventions over a real lit scene, with ImGui panels for the rig, its clips, instancing and now bone masks. Every descriptor set, UBO offset and push range comes from spirv-cross sidecars rather than a hand-written interface — reflected binding, proved by being driven.

tools/run-lab.sh --rig …/Rogue.glb --clip Walking_A --mask …
Blix.Labs.Toolchain.Probe
exe774 ln2 deps

The binding model printed — and checked. Deliberately not merged with blix-cook inspect: that lists what is in a file and always exits 0; this judges clip lengths, the skeleton, the binding contracts and now layer masks, and exits non-zero when they are wrong. They overlap in subject and not in purpose.

Blix.Labs.Toolchain.Capture
exe830 ln7 deps

Renders the lab and writes what it rendered to a PNG — the capability Blix did not have at all until this arc, since colour attachments were created without TransferSrcBit. Reproducible single-frame sampling, --xray, --frames-out, --zoom, and --lockstep as a negative control: N bodies on one clip must come back as exactly one pose fingerprint.

tools/run-lab-capture.sh
Blix.Labs.Character
lib2,018 ln3 consumers

The character lab's library — RoomCamera (382, four rigs), CharacterMotor (365), Room (301), RoomRenderer (293), RoomGeometry (196), BodyResolver (183), plus LabReport and LabTrace. Subject: contact — where a body can go and what stops it.

It has no character in it. The body is a capsule; nothing here loads a rig.

Blix.Labs.Character.Room
exe632 ln8 deps

The viewer you drive. Its central claim is one source: what is drawn and what will be swept are the same triangles, and the flat shading means every facet you can see is a facet the sweep will hit. The slope tint shades each surface by the normal the collider reads, so a mis-wound face reads as a floor standing up rather than as odd lighting.

tools/run-room.sh
Blix.Labs.Character.Probe
exe830 ln2 deps

87 checks, no window and no device — the room's ground truth is closed form, so verifying it is arithmetic. Every number in the room was authored, so "it looks like a ramp" is not the question; whether the ramp the sweep hits is the 30° the claim says is. A resolver resting at 31° and one sliding at 29° look identical in a screenshot.

Tests

4 executables · 5,390 ln · 800 checks

All four are the same shape: a CLI harness printing GREEN OK / RED FAIL per case and exiting non-zero if any fails. No test framework, no attributes — the exit code is the contract. Every claim is paired with a negative control, on the rule that a test that can only pass is not a test.

Blix.Test.Graphics
exe3,272 ln516 checks

The engine suite, CPU-only, organised into lettered sections A through AU that each pin one decision — matrix convention, barrier equality, the reflected binding model, the uniform arena, and most recently bone masks and masked blending. It began as the acceptance criteria for the row-vector matrix migration and never stopped growing.

Blix.Test.Diagnostics
exe1,603 ln206 checks

The debug system's frame lifecycle, channels, history and dump sinks. It is the suite that should have caught JsonDumpSink serialising every System.Numerics value as {} for the life of the feature, and did not — nothing asserted on a published vector's contents.

Blix.Test.Physics2D
exe238 ln43 checks

The 2D collision math. Each primitive pair gets a known overlap, a known disjoint case and — where it means anything — an edge case: touching exactly, concentric, AABB aligned with OBB. Raycasts get a hit and a miss.

Blix.Test.Physics3D
exe277 ln35 checks

The suite Blix.Geometry had never had, added by the character arc. The docs described Intersection2D as mirroring the 3D pattern and being pressure-tested by the 2D harness — so the mirror was tested and the original it mirrored was not, and had not been touched since the initial commit. It starts at the capsule because a capsule is what a character is.

05 — tools

tools/ — 23 files, three jobs

Every headed application has a launcher, and they all exist for one reason: Homebrew's dotnet is a #!/bin/bash shim, /bin/bash is SIP-protected, and dyld strips DYLD_* from its environment — so the Vulkan loader path never survives dotnet run. Each script sets the ICD and layer paths and then execs the apphost directly.

Launchers · 14
exec the apphost, never dotnet run

run-chassis · run-vulkan-hello · run-instanced · run-particles · run-vulkan-sponza · run-pong · run-runner · run-tank · run-bulwark · run-rts-game · run-lab · run-lab-capture · run-room · run-room-capture

Each carries its application's argument documentation in its header, which is where the flags are actually documented — --rig, --clip, --mask, --frames, --xray, --lockstep.

Gates & measurement · 3

gate-rts-game.sh — the RTS gate: three quick runs by default, --years adds the two simulated years. Only for RTS work; engine changes go through the four suites instead.

perf-matrix.sh — the camera and daylight matrix run as one command and tabulated from the runs themselves. perf-pacing.sh — the vsync-on pacing pass, with repeats.

Asset pipeline · 5

07 — pressure

What the graph says needs attention

Findings, not opinions — each is a number off the tree above, ordered by how much of the structure it implicates rather than by how easy it is to fix.

2.1×game vs engine

RTSGame is larger than everything it stands on

72,720 lines against the engine's 35,357, and 74% of all non-engine code. Whatever it has learned about geometry, nav, crowds and rendering has not travelled — and the empty Geometry cell says that is not an accident of style.

6skinned paths

Six independent ways to draw a skinned mesh

Runner, VulkanLit, the toolchain lab, Bulwark, RTSGame and SkinnedGameObject — each with its own vertex shader. The pose pipeline underneath is shared by all of them; only the draw is copied, because only the draw was ever baked into the abstraction.

807stranded lines

Two engine abstractions with one consumer each

SkinnedGameObject (121, VulkanLit) and PropModel (686, RTSGame). Both are shaped as shared infrastructure and neither is. A third attempt should have to clear a higher bar than the first two did — which is what stage C-0 of the character arc is written to do.

22,778lines of debug

A third of the game is instrumentation

RTSGame's Debug/ folder is larger than any engine module and four times its Rendering/. None of it is reusable by anything else, and the labs rebuilt their own equivalents — report, trace, probe — from scratch.

8,267lines, one module

Blix.Graphics.Vulkan is 23% of the engine

The largest module, split across ten VulkanGraphicsDevice.* partials plus the render graph. One dependency and 21 consumers, so the weight is contained — but swapchain and textures alone are 2,927 lines.

1unverified consumer

The array-uniform freeze has never been exercised

The prologue froze Matrix4x4ArrayUniform and built a record-time detector. VulkanSponza is the tree's only consumer of it and its asset pack is on an unmounted SSD, so the fix that started this whole arc is still unproven against the one thing that would prove it.

2folders, no csproj

src/ contains things the build graph cannot see

Blix.Shaders is three GLSL includes reached by glslc -I; Blix.Labs.Character.Motion is a deleted project's leftover bin/ and obj/. Both make ls src lie about what the tree is.
