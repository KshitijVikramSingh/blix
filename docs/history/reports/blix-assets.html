The Unfinished Cook

Blix has an asset cooker, three engine-native formats, and a documented schema for reporting which path a load took. What it does not have is any way to see any of it. This is the pipeline counted rather than described — and the count says the cook is not half built, it is built and then left silent, which is a different problem with a different fix.

01 — the shape

Cooking does not make a new asset. It makes a faster sibling.

This is the fact everything else follows from, and it is easy to miss because the word "cook" implies a transformation with an output you then use. Here the output has no address of its own.

Assets/models/
  Rogue.glb            3.6 MB   the asset. This is what you open, before and after.
  Rogue.blixmesh       257 KB   geometry only. Found by Path.ChangeExtension, used silently.

The consumer still says Rogue.glb. Nothing in any call site, any manifest, or any build step mentions the cooked file — GltfStaticImporter checks whether it exists and uses it if so. The same line of code loads a cooked and an uncooked asset, and there is no return value, log line or field that says which happened.

Three consequences fall straight out. Cooking can never be a hard dependency, because a missing sibling is indistinguishable from a source-only asset. Cooking can never be verified by a consumer, because the consumer cannot ask. And a cooked asset is not a thing you can open — which is the question the viewer arc ran into, and the reason the answer is not "a second viewer for cooked assets".

There is no cooked/uncooked split to build tools along, because the runtime deliberately erased it. What there is instead is a fact about a load that nothing can currently observe.

Read the first two rows together. kit/ is entirely cooked and models/ is entirely not — and they are the same project, the same asset vendor, loaded by the same importer. The split is not a judgement about which models are hot. The four skinned villagers and every building in the game are in the uncooked half, and they are drawn every frame.

The split is that somebody once ran blix-cook mesh and pointed it at one directory. Nothing recorded that, nothing repeats it, and nothing notices the other twenty-two.

And there are no images to cook at all

The texture half of the cooker — BC7/BC5 encoding, mip chains, Bc7Native, the whole .blixtex format — has zero reachable inputs in this repository. Not because it is unused: because of how the assets are authored.

0  .png / .jpg / .jpeg files anywhere under src/
0  of the 62 assets reference an external image URI — every texture is embedded
—  and TryResolveBlixTex can only sideload for a file URI, never for an embedded blob

So the .blixtex path is correct, tested, and cannot fire on a single asset in the tree. Its one real consumer is the Sponza pack, which lives on an external SSD outside the repository. That is worth knowing before anyone reasons about texture cook coverage from what they can see.

03 — the formats

Three engine-native formats, and where each one stops

Each is well-built and each covers less than its name suggests. The gaps are not bugs; they are the places the work was left, and none of them is written down where a consumer would find it.

.blixmesh
from .gltf / .glb · v3 · 235 lines

Packed vertex and index bytes per primitive, with LOD index chains and a world-space geometric error per level so selection can be screen-space rather than a magic distance. Replaces the seconds SharpGLTF burns interpreting accessors.

Stops at geometry. Materials are not cooked — the runtime still parses the sibling glTF in full for every factor, texture reference and alpha mode.
.blixtex
from .png / .jpg · 328 lines

A full CPU mip chain encoded to BCn by role — BC7 sRGB for base colour and emissive, BC5 for normals, BC7 unorm for metallic-roughness and occlusion. Uploaded with no decode and no runtime compression cost.

Stops at external files. An image embedded in a .glb has no path to hang a sibling off, so it is decoded from PNG at every load, forever.
.blixprobe
from .hdr · 179 lines

Equirectangular to cube, diffuse irradiance, GGX prefilter chain and BRDF LUT, all baked once. The most complete of the three — what it produces is exactly what IBL needs at runtime.

Stops at one consumer. Sponza is the only thing that bakes or reads one, and it is not in the repository.
04 — the silence

The report was written. Nothing emits it.

Blix.Diagnostics/AssetLoadReport.cs is 29 lines and names exactly the four states a load can be in. It has been there long enough to have its own documented schema comment and its own test.

public enum AssetLoadMode
{
    Source,     // original file parsed directly
    Cooked,     // engine-native binary used
    Fallback,   // desired path missing; a substitute was used
    Missing     // nothing usable; the slot is empty
}

emitters in the entire tree: 0
references: Blix.Test.Diagnostics, twice, both constructing one to check it round-trips

This is the single clearest statement of where the pipeline was left. The type that answers "which path did this load take" exists, is correct, and the only thing that has ever built one is the test that checks it can be built. Every loader that makes the decision — GltfStaticImporter choosing .blixmesh, TryResolveBlixTex choosing .blixtex, the sky falling back to procedural — makes it silently.

And the runtime never checks whether a cooked file is current.

The cook compares timestamps when deciding whether to re-cook. The loader does not: the test is File.Exists and nothing else. So a cooked sibling older than its source is used in preference to the source, with no warning, indefinitely.

var useCookedMesh = File.Exists(blixmeshPath);  — the whole check

today, in this tree: 29 of the 30 cooked assets have a .blixmesh older than its .gltf

Those 29 timestamps may well be an artifact of a git checkout rewriting mtimes rather than a real edit — that is exactly the point. Nothing in the engine can tell the difference either, and it does not look. A genuinely stale cook and a checkout are the same silence.

05 — worked

Rogue.glb, the one cooked asset outside RTSGame

What a load actually does today, and what a read-out would have said. Every figure below is observed, not modelled.

Demos.Runner/Assets/models/Rogue.glb — 3.6 MB, 6 primitives, 41 bones, 76 clips
geometrycooked Rogue.blixmesh · 257 KB · accessor interpretation skipped
materialssource the full 3.6 MB glTF parsed by SharpGLTF anyway — materials are never cooked
albedosource embedded PNG, decoded in 31 ms, every single load — no sibling is possible
reportednothing no log line, no return value, no AssetLoadReport — none of the above is observable

The cooked file is 7% of the source's size and saves the geometry pass, and then the source is opened and parsed in full regardless. Cooking this asset bought less than it looks like, and there is no way to find that out except by reading the importer.

The 31 ms figure is blix check's own line — decoded 1 images in 31 ms — which is the closest thing in the tree to the read-out this document is arguing for, and it exists on one code path in one tool.

06 — vocabulary

There is no such thing as a pack

Worth stating plainly, because the word has been doing load-bearing work in design conversations while meaning nothing in the code.

Searched across the tree, pack as an engine concept appears zero times. Every actual use means a bundle of models an artist shipped — "the CC0 pack", "the KayKit pack", "the ~19 GB Sponza pack set", where the last one is a directory on an SSD. There is no pack format, no pack manifest, no pack loader, and nothing that could open one.

The nearest real thing routes one font

AssetDatabase + AssetId + IAssetImporter + the manifest schema is 209 lines of a genuine id-to-source registry. Four projects load a manifest. All four manifests contain exactly one entry, and it is the same TTF.

Runner · Bulwark · Pong → fonts/bowlby  ·  RTSGame → fonts/hud
both resolve to BowlbyOne-Regular.font.json

FontImporter is the only IAssetImporter ever registered, anywhere
MaterialImporter 195 lines · WavImporter 134 · TextureImporter 13 — no callers

Meshes, textures and audio all bypass the database and call their loaders directly. So the addressing layer exists, works, and was overtaken — the thing that actually addresses an asset in Blix is a file path, and the cooked formats were built to match that rather than to replace it.

07 — the loop

What closing it means, and what it decides

The cook being silent and opt-in is not an oversight to patch. It was left open waiting for the tooling arc to say what it should be — so these are the decisions that arc is actually holding, stated as decisions.

D1Does a load report what it did?

The type exists and the loaders all make the decision. Emitting it turns four silent classes of behaviour — cooked, source, fallback, missing — into something a tool can show and a check can assert on.

This is the cheapest and highest-value item in the document. It is the difference between a cooker you run and a cooker you can tell worked, and every other decision below gets easier once a load can be observed.

D2Is a stale cooked file an error, a warning, or ignored?

Today it is ignored, by a check that is one File.Exists. The options are a timestamp comparison at load (cheap, and noisy across every git checkout), a content hash written into the cooked header (correct, and a format change), or leaving it and making staleness visible in the read-out instead.

I would put it in the read-out before putting it in the loader. A loader that refuses a stale file makes a checkout a build break; a loader that says the file is stale makes it a thing you look at.

D3Do materials get cooked, or does the glTF stay in the pipeline?

Right now .blixmesh saves the geometry pass and the source is parsed in full regardless, so the cook's payoff is capped by a cost it does not address. Cooking materials would mean the cooked output is finally self-contained — which is also what would make a cooked asset a thing with an address, and therefore a thing a tool could open.

This is the one that decides whether "open a cooked asset" is even a coherent request. Until materials are cooked, the answer is no — and that is a fact about the format, not about the tool.

D4Does anything ever say what is cooked, or is it whoever typed a path?

The census is the evidence: one directory fully cooked, its sibling directory untouched, same project and same importer. Coverage today is a property of shell history.

A cooker with a UI answers this by construction — it can only show you coverage if it knows what the set is. Which makes "what is the set" the first thing that UI has to decide, and the manifest is the only existing candidate.

D5Can the texture cook reach anything authored the way Blix assets are authored?

Every asset in the tree embeds its textures, and a sideloaded .blixtex needs a file URI. So the format works and the pipeline into it does not exist for in-tree content — it would need either an unpack step, or textures cooked into a container rather than beside one.

Worth deciding explicitly rather than discovering again. The current state reads as "texture cooking is unused", and the true statement is "texture cooking is unreachable by construction for how we author".

Taken together these say the same thing the tooling arc has been circling: the pipeline's missing piece is not a stage, it is a surface. Cook does real work and reports nothing; the formats are sound and cover less than assumed; the coverage is accidental and unrecorded. A viewer that opens an asset and says where each of its bytes came from is not a nice read-out on top of the pipeline — it is the first thing in the tree that could tell anyone whether the pipeline did anything.
