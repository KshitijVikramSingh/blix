What building with Blix should feel like, and the one idea that would make it true. Written from what the last two years of sessions actually cost, not from what the code says it is owed.

superseded — read the status before the argument

The central idea here is wrong, and §01 is why the rest of the work happened.

This proposed one application hosting many subjects, with six verbs falling out for free. That did not survive contact. Blix ships no central application — it ships parts, and a project builds its own tools out of them, which is what the character lab and RTSGame were already doing correctly. Five specific claims died and are enumerated, with reasons, in What Blix Ships §01:

  • the workbench — there is no one thing you open
  • room · controller · world as subjects — those are project content, not Blix things
  • a four-part subject contract — four required things is a framework
  • tool · lab · game as categories — a project is many of each at once
  • "headless is the same subject without a window" — probably false, and dropped

What survives is §01, and it is the reason every arc since exists: the cost of a session is not duplication, it is how much apparatus you must build before you learn anything — measured on the character lab at 4,265 lines split 2,137 question / 2,128 apparatus. Every document after this one is downstream of that measurement. §06's six objections are also still worth reading; Q1 (is this an editor) and Q2 (does the substrate become a monolith) were both answered, and the answers are in What Blix Ships §06.

One further correction from measurement since: the pack row in §02's grid is empty because pack is not a concept in this tree — it appears zero times in code as anything but a vendor's model bundle. See The Unfinished Cook.

01 — the lens

The cost of asking a question

Not duplication. Duplication is a symptom and a boring one. The thing that actually shapes a session is how much apparatus you must build before you learn anything.

The character lab was built to answer one question: where can a body go, and what stops it? Answering it took 4,265 lines across four projects — and roughly half of that is not the question. It is the equipment for asking one.

character lab · 4,265 lines · the split
the question — 2,137
the apparatus — 2,128
The question — the room, its geometry, the motor, the resolver, the camera rigs, and the checks that judge them The apparatus — a renderer, shaders, three app loops, panels, argument parsing, image readback, two launchers

the question

  • Room 301 · RoomGeometry 196
  • CharacterMotor 365 · BodyResolver 183
  • RoomCamera 382
  • Probe checks ~710

the apparatus

  • RoomRenderer 293 · shaders 172
  • Room/Program 632 — loop, input, panels
  • Capture/Program 343 — camera, readback, args
  • LabReport 180 · LabTrace 118
  • Probe harness ~120 · 4 csproj 143 · 2 launchers 88

And none of that apparatus was the first of its kind. The toolchain lab had already built every piece of it, one arc earlier, and the character lab could not reach any of it — so it wrote its own, and wrote it well, and the cost was half the lab.

To ask Blix a question, you currently have to build an application. That is the experience problem, and everything else in these documents is downstream of it.

The same tax shows up everywhere once you look for it. To fit a model's pivot you build an overlay and read numbers off it by eye. To check whether a change broke anything you run five executables and read five outputs. To look at an asset you need to know a project path and which of three tools takes --rig versus --model. None of these are hard problems. They are all the same problem: there is nowhere to put a question except a new program.

02 — the thesis

Verbs are shared. Subjects are contributed.

Everything Blix's tooling does is a small set of verbs applied to a growing set of subjects. Today every pairing is its own executable, which is why there are eight command-line entry points, two UI applications, fourteen launchers, and no way to ask a new question cheaply.

The verbs are stable and there are about six of them. The subjects are the interesting part and there should be many. Write the grid out and the proposal states itself — the cells are not things to build, they are things you get:

subject ↓   verb → opencheckshottracebenchcook
modela static glb viewer --model probe capture free — blix-cook
rigskeleton + clips viewer --rig probe capture free — cook-character.sh
roomauthored geometry Room a 2nd app Probe a 2nd probe Capture a 2nd capture LabTrace — —
controllera body that moves not built not built not built not built not built —
framepasses, draws, uniforms overlay per app VALIDATE=1 — --dump-frame perf-matrix.sh —
worldan RTS map + sim the game 35 scenarios — StateFingerprint FightBenchmarks —
packa cooked asset set — — — — — cook-sponza

Read the grid down a column and it is one verb implemented four to six times. Read it across a row and it is one subject that had to implement every verb itself before it could use any. The empty cells are not missing features — most of them are things nobody could justify building a whole application for.

The proposition is to invert it: the verbs become the substrate, and a subject is the only thing you write. Register a subject and every column you did not implement arrives anyway — you get shot because the workbench knows how to render and read back, you get trace because it knows how to write frames to disk, you get a headless mode because headless is just the same subject without a window.

blix open  character:room        headed, panels, gizmos
blix check character:room        headless, judges, exit code
blix shot  character:room --out ramp.png
blix open  rig:Assets/Rogue.glb --clip Walking_A --mask spine
blix check pack:sponza
blix bench world:rts --years 2

One argument surface, so --clip means one thing. One place to look, so there is nothing to remember. And a new question costs the question.

03 — the contract

What a subject is, and what it gets

The substrate is not a library of shared parts you go and fetch. It is a host, and a subject is a thing it hosts — the same move Blix.Demos.Chassis already proved at the application level, one level up.

what a subject brings

  1. Content — what to draw. Triangles, a rig, a map, nothing at all.
  2. State — what is currently true of it, and how a fixed step advances that.
  3. Panels — its own read-outs, as objects that take what they draw rather than methods that call back into an app.
  4. Checks — what it claims, and how to falsify it. The headless verb is built out of these.
the character lab, restated: Room · RoomGeometry · CharacterMotor ·
BodyResolver · its panels · its 87 checks

what the workbench brings

  1. A scene — shadow, lit HDR, present, a grid, a sun.
  2. A camera — orbit for looking, and whatever rigs a subject adds.
  3. A shell — window, docking, the embedded viewport, picking, selection.
  4. Gizmos and channels — debug draw, trails, report, trace.
  5. Both modes — headed with a window, headless without one, from the same subject.
  6. An address — the moment it exists it is blix open <name>. No project path, no launcher, no argument parser.
what the character lab wrote for itself, twice over, in ~2,100 lines

The same session, before and after

today — "is a 30° ramp climbable?"

  1. Create a library project and three executables
  2. Write six shaders and a render graph
  3. Write a camera, a scene, a grid
  4. Write an app loop, input, ImGui panels
  5. Write argument parsing, three times
  6. Write image readback and camera framing
  7. Write two launcher scripts
  8. Write the room and the motor
  9. Ask the question
≈ 2,100 lines before step 8

after

  1. Write the room and the motor
  2. Register the subject
  3. blix open character:room
  4. Ask the question
  5. Later: blix check character:room in the same breath as everything else that is checked
the apparatus is not yours to write, or to maintain, or to get wrong twice

The second column is also what makes a lab genuinely deletable. Motion was deleted correctly and it still cost a project, a launcher and a set of shaders to remove. A subject is deleted by deleting a file.

04 — the words

What this makes of tool, lab and game

The three words stop being categories of project and become roles in one system. That is the part I would most want to argue about, because it is the part that changes how everything is named.

A tool
A verb.

Not a project. open, check, shot, trace, bench, cook. There are about six, they are written once, and adding a seventh is a real event rather than a Tuesday.

A lab
A subject with a question.

Content, state, panels, checks — and an expiry date. It is allowed to be wrong and expected to be deleted. What it is not any more is an application, a render graph, a set of shaders, and three executables.

A game
A subject that outgrew the workbench.

It owns its own window and loop, because shipping demands it. But its world can still be a subject for the headless verbs — which is what RTSGame's 35 scenario files already are, written by hand.

And "first class" stops meaning packaged. A dotnet tool on PATH was never the goal — the goal is that a thing you wrote is addressable and complete the moment it exists. Under this shape it is, and the fourteen launchers collapse into one script for a reason that has nothing to do with NuGet.

05 — pipelines

What the workflows look like when they are good

Sketched broadly, as asked — these are compositions of verbs over subjects, and writing them this way is what exposes the missing ones.

bring content in
  blix cook   pack:kaykit/rogue          textures, meshes, clip merge
  blix check  rig:rogue                  skeleton, clips, bounds — exit code
  blix open   rig:rogue                  look at it, fit the pivot with a read-out
                                          rather than by eye through an overlay

prove a change
  blix check  --all                       every subject's checks, one verdict
                                          today: five executables and a person reading five outputs

keep the evidence
  blix shot   character:room --out ramps.png
  blix trace  character:room --frames 200
                                          the same pair that found the ramps facing a wall — twice

measure
  blix bench  world:rts --years 2
  blix bench  frame:sponza --matrix        perf-matrix.sh, addressed instead of scripted

Two things fall out of writing them down. The first is that blix check --all is probably the highest-value thing in this entire document — it is the step run most often in a session, it currently costs five invocations and a human, and it is nearly free once subjects carry their own checks.

The second is that the gaps become obvious and small. A pivot-fitting read-out is a panel on the rig subject. A licence check is a field on the pack subject. Neither is worth an application, which is exactly why neither exists.

06 — argue with this

What it risks, and the questions I would sit with

The proposal is strong enough to be worth attacking properly. These are the places I think it is most likely to be wrong.

Q1Is this an editor, which every plan in this repo says Blix will not build?

Four plan documents list "an editor" under what an arc will not build. This proposal is one window with panels, docking, a viewport, picking and a scene graph in it. From a distance the difference is not obvious, and "we are not building an editor" has been load-bearing.

My answer, and I think it holds: an editor authors. It writes content back out, owns a project format, and becomes the way you make things. A workbench only ever reads and judges — it opens what exists, shows it, and says whether it is sound. The line is whether it ever writes an asset. I would put that in the plan as a hard boundary, because it is the one that stops this becoming Unity in four years.

Q2Does the substrate become the monolith the engine deliberately does not have?

Every module in Blix today is small and takes few dependencies — Blix.Core is 483 lines and 22 consumers. A workbench that hosts everything would be the first thing in the tree that everything tool-shaped depends on, and the first place where a bad decision is expensive to reverse.

Partly mitigated by it sitting outside the engine — no game would depend on it. But it is real, and it is the argument for the subject contract being very small: four things in, six things out, and nothing clever.

Q3Does a subject's headless twin actually generalise?

The proposal leans hard on "headless is the same subject without a window". That is true for the room and the rig. Is it true for a frame? For an RTS world that needs a whole simulation running before anything is checkable?

Unsure. This is the assumption most likely to break, and the cheapest way to find out is to write the contract against the two hardest subjects first — frame and world — rather than the two easiest.

Q4Who owns the window when a subject wants one?

A game owns its loop. A lab does not. If both are subjects, something has to give — either the workbench hosts the loop and a game can never be a subject, or subjects can take the loop and the shell becomes optional.

I would let games out of it entirely at first: games are subjects for the headless verbs only. It keeps the contract small and it matches what RTSGame already does.

Q5Is "one window, many subjects" actually better than several small tools?

The opposite design is real and has a good track record: many small, sharp tools that do one thing. This proposal argues for one because the apparatus is what is expensive, not the tool. But that is an argument, not a fact.

I hold it loosely. The strongest evidence for one is that the viewer already handles two subjects — models and rigs — in a single app, and the panels changing is what makes it work rather than what strains it.

Q6What does this cost, and what does it cost to be wrong?

Roughly: the substrate is most of what the two lab libraries already are, rearranged behind a contract. The expensive part is not writing it, it is that every existing tool and lab has to move onto it or the tree ends up with both.

Which argues for proving the contract on one subject end to end before anything is renamed — and for the character controller being that subject, since it is the one question already queued and it needs the rig, the room, panels and checks all at once.

A proposal, not a plan — nothing here is staged, ordered or committed to.
