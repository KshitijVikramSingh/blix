What Blix Ships

Not an editor, not a game, not a lab. Tools, formats, pipelines, conventions, and a substrate deep enough that you can pick any two points in the stack and build a CLI or UI tool between them.

01 — corrections

What died in the last draft

Three of them were the centrepiece, so this is not a revision so much as a different argument that happens to reuse some numbers.

the workbench
one app, many subjects

There is no central application. Blix does not ship one thing you open. It ships the parts, and a project builds its own tools out of them — which is what the character lab and RTSGame were already doing, correctly. What was wrong was never that they built their own; it was that building one cost two thousand lines of apparatus first.

room · controller · world
as subjects

Those are project content, not Blix things. A room is something the character lab made up. Blix has no opinion about rooms and should not learn one. The things Blix actually has are the artifacts it defines and the frames it draws.

a subject contract
content · state · panels · checks

That list should have ended at "anything, or nothing". Four required things is a framework, and a framework is exactly the thing that imposes opinions downstream. Whatever a caller has, it hands over; whatever it does not have, it does not.

tool · lab · game
as categories

Dropped. They were categories of project, and projects are not the unit. A project is many bespoke tools and games at once — RTSGame is a game plus 35 headless scenario runners plus a tuning UI, in one project, and that is the right shape rather than a confusion to tidy up.

headless is the same
subject without a window

Probably false, and dropped as an assumption. A headed tool and a headless one share a library and nothing else. Three programs over one library is the shape that already works; forcing them into one mode switch would have been the framework again.

Two objections I raised were also answered and I accept both. On monolith: size is not the fault — the Vulkan layer is 8,267 lines and is good engineering, because its job is well defined, it is boxed in one place, and it imposes nothing on what comes after. That is the test, not line count. On cost: this tree already replaced its entire graphics backend once. Restructuring is not the risk.

02 — the statement

The five things, and the one sentence

Blix does not ship an editor, or a game, or a lab. It ships tools and formats and pipelines and conventions and a substrate big enough that you can pick any two points and build a CLI or UI tool around it.

Formats

The file types Blix defines and owns end to end — written, read, listed and judged by its own code.

.blixmesh · .blixtex · .blixprobe
+ what glTF becomes on import
Pipelines

The transformations between them. Deterministic, re-runnable, and reporting what they did rather than only that they finished.

cook textures · cook meshes
clip merge · LOD chains · spatial split
Tools

The small number of things Blix itself invokes over its own formats. Everything else is a project's own business.

inspect · check · cook · open · shot
Conventions

The rules that make a bespoke tool recognisable as a Blix tool without any shared code at all.

OK/FAIL + exit code · negative controls
proves/owns blocks · the §-numbered index
Substrate

The stack itself, with seams you can enter and leave at. The subject of the rest of this document.

bytes → import → cooked → CPU
→ GPU → draw → graph → device → image

The consequence worth stating plainly: "each project is many editors and many games in one project" is not a description of a mess, it is the target. A project builds the bespoke tools its own content needs — a map tuner, a fight bench, a determinism check, a room viewer — and Blix's job is to make each of those cost the thing it is about and nothing else.

03 — the artifacts

Two things Blix actually has

Once room, controller and world are gone, the list is short — and it gets shorter still when the first three collapse into one.

A pack — content at rest corrected

A named set of content that travels together. A .glb is a pack in that sense: it carries meshes, a skeleton, clips, materials and textures in one file. So model and rig are not separate artifacts — they are the same file, and the tools should discover what is inside rather than be told by a flag. blix open rogue.glb should need no flag, and the panels that appear should be the panels its contents justify.

Two claims in the last revision did not survive being measured, and both matter. "A cooked Sponza directory is a pack" is false — cooking produces siblings, not a set: .blixmesh holds geometry only and the source glTF is still parsed in full for every material, so no cooked output is self-contained and none of it has an address of its own. And pack is not a concept in this tree at all — it appears zero times in code as anything but a vendor's model bundle. The nearest real registry, AssetDatabase + manifest.json, is 209 lines routing one TTF in four projects.

So the word is worth keeping as the noun the verbs take, and worth not mistaking for something that exists. What actually addresses an asset in Blix is a file path — see The Unfinished Cook for the census, the three formats and where each one stops.

A frame — content in motion

The other real thing, and the one Blix uniquely owns: passes, targets, draws, uniforms, bindings, timings. It is not a pack and it is not on disk. It already has the beginnings of tooling — --dump-frame, BLIX_VK_VALIDATE=1, the record-time fingerprints, the overlay — all of which exist in different places with different shapes.

And the verbs re-read

blix inspect <pack>          list what is in it. exits 0. reports.
blix check   <pack>          judge what is in it. exits non-zero. judges.
blix cook    <pack>          transform it into Blix's own formats
blix open    <pack>          look at it
blix shot    <pack>          look at it, without looking

blix frame   --dump | --validate | --bench     the other subject, barely tooled

The inspect/check distinction is already in the tree and already deliberate — blix-cook inspect lists and always exits 0, the probes judge and do not. That is a convention worth keeping exactly as it is; it just needs one noun to apply to.

Shared libraries, counted once rather than apportioned: Blix.Tools.Studio 2,261 across five consumers (viewer, capture, probe, shell, its suite) and Blix.Labs.Character 2,018 across three. Both were written for the rows above them and exist for no other reason.

Every tool that stops before P4 costs a few hundred lines of its own. Every tool that reaches P8 either costs one to two thousand — or sits on a library that size written for it. The character room is 633 lines on top of 2,018. The stack is thin in exactly one place, and it is the place between having data and seeing it.

That is a much narrower diagnosis than "the labs hold things that should be shared". It says: P0→P3 is already good substrate — an importer you can call, CPU data you can hold, and a convention (OK/FAIL, exit code) that makes a 252-line tool complete. Five tools in this chart are cheap for exactly that reason, and three of them are not even in a lab.

And it says P4→P8 is not substrate at all. It is a thing each tool builds from scratch: a render graph, a set of shaders, a camera, a window or a readback path. Nobody has ever spanned to the screen cheaply, which is why so few tools do, and why the ones that do are the most expensive artifacts in the tree.

05 — what is owed

What the substrate has to provide, derived from the chart

Five things, all of them in the P4→P8 gap, none of them a framework. The test each has to pass is yours: a well-defined job, boxed in one place, a stable surface, and no opinion imposed on what comes after.

Two of the five have landed since revision 2, and their today lines now record what happened rather than what is missing. The studio arc took the scene; the shell took the widget. Both are marked below, and neither was extracted under pressure — they were authored, which was the argument for doing them at all.

P4

Residency — data on the GPU without a draw attached

Vertex and index buffers, textures, material scalars, bounds, from CPU data or straight from a pack. It names no shader, no material set, no pass and no instance count, because the moment it does it has an opinion about how you will draw.

today: six implementations, the two engine-side ones stranded at one consumer each
P6

A scene that can show a thing

Shadow → lit → present, a grid, a sun, a camera. Not "the lab scene" — a default that a tool takes when it has no opinion, and replaces entirely when it does.

landed — Blix.Tools.Studio, 2,261 lines: one graph, a ladder from knobs to bring-a-draw to append-a-pass, and the look declared as [Tune] so every tool on it gets a Scene panel and --sun-elevation without parsing one. Five consumers, one of them headless with no device at all.
P8

Readback as a call, not a program

Render n frames, hand back an image. The capability arrived this year — colour attachments were not legal copy sources before it — and it still exists as whole programs rather than as something you can call.

still open — Blix.Tools.Shot 944 + Character/Capture 344, both of them a camera, an argument parser and a readback path around one ReadTexture.
UI

A window with panels, without an application

The chassis already gives a window, input, a loop and ImGui. Above it, the embedded viewport is now a widget a tool calls — it reports Clicked and the caller casts its own ray. What deliberately did not move is the frame layout and the selection: a thing that invokes your code is a host, and a tool's panel order is its identity.

partly landed — Blix.Tools.Studio.Shell, 167 lines, one widget. Still in an executable: ViewerPanels.cs 625 + StudioSelection.cs 129 — and the second is per-asset-kind work that belongs beside a mesh view and a rig view, not in a shell.
P0–P2

The formats as first-class citizens

Three formats are defined and written — .blixmesh, .blixtex, .blixprobe — and the only way to see inside one is a cooker subcommand. Each should be listable, judgeable and openable, because a format you cannot inspect is a format you debug by printf.

still open, and now measured — blix-cook inspect, and nothing that can open a .blixmesh, .blixtex or .blixprobe. Worse than unopenable: AssetLoadReport names the four states a load can be in and has zero emitters, so which path a load took is not observable either. See The Unfinished Cook.

Nothing in that list is a host, a plugin system or a contract a caller has to satisfy. They are five pieces you can call, in the gap the chart points at. A tool that spans P3→P8 should cost what a P3 tool costs — a few hundred lines, most of them about its subject.

06 — state

Settled, and still open

settledBlix ships no editor, no game, no lab

It ships formats, pipelines, tools over its own formats, conventions, and substrate. A project builds its own bespoke tools and games together, as RTSGame already does. The editor question dissolves: there is no application to become one.

settledSize is not the monolith test

Well-defined job, boxed in one place, stable surface, no opinion imposed downstream. The Vulkan layer passes it at 8,267 lines. Each of the five pieces above has to pass the same test individually, which is mostly a constraint on their surfaces rather than their size.

openWhether a load may stay silent

Every loader that chooses between a cooked file, a source file and a fallback makes that choice without saying so, and AssetLoadReport — the type that names the four states — has zero emitters. Cooking was left opt-in and quiet on purpose, waiting for this arc to say what it should be.

This is the cheapest high-value item in either document, and it is what makes a cooker checkable at all. Five decisions it forces are laid out as D1–D5 in The Unfinished Cook.

settledHeaded and headless do not unify

Three programs over one library, which is the shape that already works. Dropping this also removes the main reason the last draft wanted a contract.

settledWhere the window and the loop sit

A tool is an application and calls the pieces. The test that decided it is mechanical — who calls whom: a thing you invoke inside your own ImGui.Begin is a library; a thing that invokes your code is a host. So the viewport became a widget and the frame layout did not move, because a tool's window title, panel order and what it says when nothing is loaded are its identity.

Settled by building it rather than by arguing it, which is why it is here as state rather than as a proposal. Blix.Tools.Studio.Shell is 167 lines.

openDoes a pack know what it is?

Dropping --model and --rig means a file reports its own contents and tools react. Clearly right for glTF, where the file says. Not askable of a cooked directory, because measurement since says there is no such artifact — the cook makes siblings, materials are never cooked, and nothing produced is self-contained.

So the question splits, and the smaller half is answerable now: the flag goes, and what the viewer shows is decided by what the file is. Whether "pack" ever becomes a real type waits on whether materials get cooked — which is the thing that would give cooked output an address at all. That decision is now written down as D3 in The Unfinished Cook.

openWhat the frame subject actually is

It is the one thing here Blix uniquely owns and the least tooled: a dump flag, an environment variable, a fingerprint, an overlay, all differently shaped. Whether that becomes one addressable artifact or stays a set of habits is undecided, and I have not thought about it as hard as the asset side.
