What Blix Tooling Should Be

Boundaries before stages. What a UI tool in this tree is actually made of, which parts are shared, what the words tool and lab have to mean for the next case to be decidable, and what a front door can and cannot be on this platform.

Everything below is tagged: evidence counted off the tree · position mine, argued, redirectable · open not mine to settle alone.

00 — corrections

Three things this pass changed

Written first because two of them were in yesterday's plan and one was in the topology page. Both documents are wrong until amended.

RTSGame's Debug/ is not UI, and not duplicated instrumentation

It is 35 files of headless scenario runners — FightBenchmarks, DeterminismCheck, StateFingerprint, MovementStressScenarios, StallCensus, MapSweep. Exactly one file in it touches ImGui. It does not overlap the labs' LabReport/LabTrace, which are live-session instruments.

The topology page says "both labs rebuilt their own report and trace from scratch" as if it were the same job. It is not. The real finding is better: "run headless and judge, exit non-zero" now has three implementations — the four test harnesses, the two lab probes, and these 35 scenario runners. None share a line.

There is exactly one real UI tool in the tree

Ten files mention ImGui. Two are the renderer and the contributor interface, two are the shared diagnostics overlay, one is the chassis spec, one is a demo, one is RTSGame's map tuning. That leaves two applications with panels of their own: the toolchain viewer (ViewerPanels.cs, 717 lines) and the character room (inline in its Program.cs, 632 lines).

So "UI tooling" is not a category with several members that need organising. It is one worked example and one improvisation, and the question is what the second one should have been able to build on.

The embedded viewport lives inside an executable

Everything the view arc built — ImGui textures, the embedded viewport, offset and Retina picking — is in Blix.Labs.Toolchain.Viewer/ViewerPanels.cs and LabSelection.cs. Not in the lab library. Not in the engine. In the one place in the tree that nothing else can reference.

This is the sharpest single instance of the whole problem: a completed arc's output, filed where it cannot be used twice. And it is why the character room's UI is inline in a Program.cs — there was nothing to build on, so it built nothing.

01 — anatomy

What a UI tool in Blix is made of

Seven layers, derived by taking the two applications that exist apart. The lives now column is what makes the argument — read down it and the shape of the problem is that almost nothing is at the level its consumers are at.

RoomRenderer builds room-shadow / room-hdr / room-scene-depth → room.shadow → room.lit. The difference between them is a string prefix and one extra pass.

02 — the words

Tool, lab, and whether there is a core

The definitions should fall out of the layers rather than be asserted over them. Reading the anatomy, they do — and they give a cleaner test than the one I proposed yesterday.

ToolL1–L5 + a shell
Its subject is the content itself.

A tool opens what you give it. It has no world of its own, holds no simulation, and is finished when it can show and judge any asset of its kind. You use it while doing something else, which is why it must be findable without knowing a project path.

  • The toolchain viewer, probe and capture
  • blix-cook
LabL6 + a subject
It has a world, and a question about it.

A lab builds content of its own to ask something — a room with authored ramps, a body that sweeps. It is finished when the question is answered, and it is allowed to be deleted. Motion was, correctly, inside one session.

  • The character lab: room, motor, resolver
  • Motion, while it lasted
CoreL1 + L4 + L5
What both are made of and neither owns.

The preview scene, the read-outs and the shell. Not a grab-bag: it is exactly the set of layers that both a tool and a lab need, that neither a game nor the engine has any use for. L2 is not in it — that goes to the engine, because games want it.

  • Today: split across two lab libraries and one executable

The test this gives, and why it is better

position Yesterday's test was "does anything outside its own family need it" — a reachability question, which is circular: nothing outside can need something that was never made reachable. The anatomy gives a better one, and it is about the subject rather than the references:

Does it bring its own world?

  no   →  it is a tool.  Name it for the content, put it behind the front door,
          and expect it to outlive the arc that built it.

  yes  →  it is a lab.  Name it for the question, keep it out of the front door,
          and let it be deleted when the question is answered.

Applied backwards it predicts what happened: the toolchain family brings no world — it survived three arcs and grew three executables. Motion brought a state machine of its own — deleted inside a session. The character lab brings a room — still a lab, and should stay one.

03 — the tools themselves

Which UI tools should exist

You named UI tooling as the major utility, and the rig/model/animation inspection work as the thing already trying to be it. So this is the question the boundaries are in service of, not a detail after them.

One tool, not three

position The candidates look like three tools — an asset inspector, a rig and animation inspector, a scene inspector. They are one tool with three subjects. Every one of them is the same motion: open content, put it in a preview scene, draw read-outs over it, judge it. What differs is which panels appear, and panels are the cheapest thing in the list to vary.

Three separate applications would mean three L1s, three L5s and three sets of camera and viewport code — which is precisely the tree we already have, with two of them. The viewer already proves the opposite works: it handles --model (a node tree) and --rig (a skeleton and clips) in one application, and the panels change.

What the one tool needs that it has not got

Named from the gaps rather than from a wish list:

  • A subject beyond one file. Today it opens a glb. A scene, a room, a cooked pack and a frame are all things you have wanted to look at.
  • Panels that are objects, not methods on the app. ViewerPanels takes a ViewerLoop and calls back into it. Nothing else can host a panel from it.
  • The headless twin, as a first-class mode rather than a second executable. The probe and capture already exist and already share the library — what they do not share is the argument surface, so --rig means slightly different things in three places.

open Whether the scene/room subject is the character lab growing a panel set, or the tool learning to open a Room. These are different answers about where the boundary sits, and I do not think the evidence settles it.

04 — the front door

What "a dotnet tool" would actually mean here

I put PackAsTool in yesterday's plan without testing the premise. Having looked at what the 14 launchers are for, I think it is probably the wrong mechanism, and the reason is worth stating because it also says what the right one is.

What the launchers are actually doing

evidence Every one of them sets VK_ICD_FILENAMES, VK_LAYER_PATH and DYLD_FALLBACK_LIBRARY_PATH from brew --prefix, then execs the apphost — because Homebrew's dotnet is a #!/bin/bash shim, /bin/bash is SIP-protected, and dyld strips DYLD_* across that exec. They are not a packaging failure. They are a correct response to a platform constraint.

Why packaging does not remove it

position A globally installed dotnet tool still needs MoltenVK and the Vulkan loader from Homebrew, still needs those three variables, and is still launched through a generated shim — the same class of process that strips them today. Packaging changes where the binary lives; it does not change native loading. It would also add three costs this tree does not currently pay: runtime assets and compiled .spv sidecars have to be packed, and an installed tool drifts from the repo it was built from — which for an engine whose tools change in the same commit as the code is a liability, not a convenience.

What the front door should be instead

./blix                 one script at the repo root. The prologue lives here, once.
                          It is 11 lines and it is the reason the other 14 exist.

Blix.Cli              one multiplexed executable it execs, with the subcommands.

blix view|shot|check   content verbs → the preview tool, headed or headless
blix cook|inspect      asset verbs   → the cooker
blix test|bench        judgement verbs → the harnesses

The win was never "it is a dotnet tool". The win is one of it instead of fourteen, with one argument surface. A script is the honest home for a platform's native-loading rules, and hiding it inside a NuGet package would make it harder to read, not easier.

open Whether Blix.Cli dispatches in-process (one exe, subcommands as code) or execs the existing executables (one exe per verb, script-thin dispatch). In-process gives one argument parser and one startup; exec-ing keeps the probe and capture independently runnable and testable. I lean in-process for the headed verbs and exec for nothing, but it is a real fork.

05 — workflows

The pipelines, sketched from what is already done

You asked whether we can form opinions now given the number of uses. We can — these are not hypothetical, every one of them has been run this year. The dashed steps are the ones that exist only as a habit, with no tool behind them.

Bring content in
the most-run, least-tooled
acquire CC0→ licence check→ blix inspect→ character_merge.py→ blix cook→ pivot fit→ blix check

Two steps have no tool. The measured-pivot fit is done by eye through an overlay and written into a game's source as constants; the CC0-vs-CC-BY check is a habit. Both are exactly the kind of thing that a UI tool with a numeric read-out replaces.

Look at content
the one that works
blix view→ panels→ blix shot

The tool exists and is good. What it lacks is reach — it opens a glb and nothing else, and its shell cannot be borrowed by anything that wants to look at something different.

Prove a change
four suites, by hand
4 test exes→ probe→ BLIX_VK_VALIDATE run→ capture→ one verdict

Five invocations and a human reading five outputs. This is the workflow run most often in a session and the one with the least support — blix test returning one exit code over all of it is probably the single highest-value verb in the list.

Run headless and judge
three implementations
Test.* harnesses lab probes RTSGame/Debug ×35

All three do the same thing: construct a scenario with no device, run it, print OK/FAIL, exit non-zero. None share a line. This is the finding that replaces the wrong one about instrumentation, and it is the strongest un-acted-on duplication in the tree after L2.

Measure
shell, tabulating shell
perf-matrix.sh→ perf-pacing.sh→ perf/ ×154

Works, and is the one area where shell is the right answer — it is running an executable many times and tabulating. Left alone.

position On filing versus extracting: the L5 shell has one consumer, so §4 would say leave it. I think that reads the rule wrongly here. Extraction is moving something up so a second consumer can reach it, and it is what should wait for evidence. Moving something out of an .exe into the library it is already part of is filing — it adds no abstraction, exposes no new surface, and the only thing it changes is whether a second consumer is able to appear. The view arc's viewport has been unreachable for two arcs, which is not evidence that nothing wanted it.

07 — open

What I am not deciding alone

Each of these changes the shape materially and none is settled by anything I can count. My leaning is marked where I have one.

Is the tool core one library or three?

L1 + L4 + L5 could be Blix.Tools.Preview as a single library, or split into a scene, a gizmo set and a shell. One is simpler and risks becoming the grab-bag §5 warns about; three is honest about the layers and is three csprojs for two consumers.

Leaning one, with the layers as folders — split it when a consumer wants the scene without the shell.

Where does the preview tool's subject boundary sit?

Does the tool learn to open a Room — making it a general content viewer with a scene subject — or does the character lab grow panels of its own on the shared shell? The first makes one tool that sees everything; the second keeps labs genuinely deletable.

No lean. This is the one that decides whether "lab" stays a real category.

Does Blix.Cli dispatch in-process or exec per verb?

In-process gives one argument parser, one startup, one place where --rig means one thing. Exec-per-verb keeps the probe and capture independently runnable, which is how they are used in CI and in every session transcript so far.

Leaning in-process, with the existing executables kept as thin wrappers during the transition rather than deleted on day one.

Do the three headless-judging implementations share a spine?

Four test harnesses, two lab probes, 35 RTSGame scenario runners. All print OK/FAIL and exit non-zero. Either that is a missing module or it is a convention that is working precisely because it is not a module.

Suspicious of extracting this. A test harness that depends on a framework is the thing most likely to fail silently, and "exits non-zero" is a contract that needs no code to share.

Does any of this land before the character branch merges?

26 commits and ~7,300 lines sit unmerged on character-lab. Everything above touches project names and file locations, which is the worst possible thing to do alongside an open branch.

Land the branch first. Not because the work is finished, but because renames and an unmerged branch are the one combination that makes both harder.
